# Agent Note: Zed-ready ACP authentication, session modes, and the plan-review bridge

Status: implemented

English | [中文](2026-09-06-zed-acp-auth-and-session-modes.zh.md)

## Problem

The automation-only ACP bridge answered Zed's client model only partially. The [ACP registry](https://github.com/agentclientprotocol/registry) hard-requires a non-empty `authMethods` list with an `agent`- or `terminal`-type method, but the bridge advertised `authMethods: []` and a no-op `authenticate`, so Zed had no sign-in flow and the registry would reject the agent. Zed's mode picker had nothing to switch because the bridge advertised no session modes, even though the harness ships plan mode and the shipped `dsh-base` bundle already mounts `plan-mode` and `user-questions` in every profile that layers on it. Plan mode itself dead-ended: `exit_plan_mode` asks the user through the user-questions waterfall, which no ACP client ever answered, so a Zed-driven agent could enter plan mode but never complete its own review flow.

## Decision

**Authentication is an advertised, stateless credential check.** `initialize` returns the one agent-type method `deepseek-api-key`; `authenticate` resolves the configured credential reference (`apiKeyEnv`, default `DEEPSEEK_API_KEY`) through the credentials seam — falling back to the launch environment when no seam is mounted — and validates it with the same `normalizeApiKey` rule the DeepSeek provider applies per request. Authentication holds no state and grants nothing; a client that skips it still reaches a session whose first model request fails with the provider's own `MISSING_CREDENTIAL`. `session/new` deliberately does not re-check the credential: the bridge is provider-agnostic (tests and automation clients mount non-DeepSeek routes), so a DeepSeek-key gate there would refuse sessions that need no key. The failure point stays the earliest one that can actually know.

**Session modes are the plan-mode service, read live.** The bridge maps the fixed pair `default`/`plan` onto `planMode.get`/`planMode.set`. `session/new` and `session/resume` return the current mode state only when the deployment composed plan-mode; without it the field is absent and `session/set_mode` rejects with invalid parameters. A selection during an open turn queues inside the plan-mode service and commits at the next accepted pre-step — the bridge returns the still-current state and lets the committed change speak through the wire: the durable `plan/mode` event drives a `current_mode_update` notification from the same `session/event` listener that projects other updates, so a resumed, forked, or externally switched session reports the truth instead of a bridge-local mirror.

**User questions ride the permission channel.** The bridge answers `user-questions/request` for owned agents by mapping each option-only question onto one `session/request_permission` round trip with a synthesized `acp-question:` tool-call id. A plan-review intent maps its approve label to `allow_once` and every other option to `reject_once`; without an intent every option is `allow_once`, because the label, not the kind, carries the choice. Free-text and multi-select questions have no ACP v1 carrier (`session/request_input` does not exist in the pinned SDK), so the bridge delegates them to the waterfall, whose no-answerer failure names the gap. A `cancelled` outcome raises `ASK_CANCELLED`, which the plan-mode exit tool already interprets as "the user dismissed the review to speak instead".

**Cancellation is dispatched first.** The SDK's `ConnectionBuilder` routes every incoming message through a sequential handler chain — one dispatch hop per registered method — so the cost and timing of processing any message grows with the handler count registered before its own. The `session/cancel` notification therefore registers before every request handler. This isolates cancellation latency from future method additions, which otherwise silently re-schedule every admission-to-followup cancellation race; the "honors cancellation in the admission-to-followup handoff gap" test pinned exactly such a schedule and flipped when `session/set_mode` joined the chain.

**The registry listing is prepared, not submitted.** `packages/acp/acp/registry/` holds the manifest draft ([agent.json](../../../../packages/acp/acp/registry/agent.json)) and the monochrome [icon.svg](../../../../packages/acp/acp/registry/icon.svg); this note owns the submission checklist. Submission waits on a stable all-numeric npm release because the registry rejects prerelease versions — both the entry `version` and the `distribution.npx.package` pin must carry the same stable `x.y.z` release of `@deepseek-ai/dsh`, the icon must stay 16×16 monochrome `currentColor`, and the registry's own tooling validates the manifest and the auth requirement. The npx distribution entry pins `@deepseek-ai/dsh` and the registry re-syncs versions from npm automatically, so ordinary harness releases require no registry work.

**MCP stdio commands resolve against the harness PATH.** The ACP spec names `McpServerStdio.command` an absolute path, and the bridge used to reject bare names — but editors such as Zed forward their configured context servers with bare commands (`npx`, `uvx`), which broke every session that inherited such a server. The bridge now resolves the command explicitly at mount: an absolute path passes through, a bare name resolves against the harness process PATH — the exact environment `dsh-mcp-client`'s scrubbed-parent env hands the MCP child — and an unresolvable name fails loudly naming the searched command. The authorization contract keeps its substance: the client still launches the one absolute executable recorded at mount time.

**Agent presets join through the roster service.** The acp bundle now mounts `dsh-agent-presets` (default `standard`) and disables the same host-plane model-facing rows the web bundle disables, so the preset a session joins owns its tools, prompt sections, and skills instead of them leaking from the host plane. Creation resolves the roster default, records it in the session header, and mounts it in the factory setup (a broken preset rolls the session back); resume reads the durable `agentPreset` projection and rejoins that composition. The ACP surface for choosing is a `preset` config option: switching goes through the roster's serialized blank-session contract (`select`), so a switch after output is a caller-correctable refusal, and the committed switch lands in the session log. Services the bridge reads per agent — plan mode above all — resolve through the roster's per-agent read (`serviceFor`), because a preset-joined Agent's scope context cannot see its preset's entry-local realm instance; a rosterless deployment falls back to the host plane.

**Permission presets are a live config option.** The bridge also surfaces the permission service's preset table (`read-only`, `workspace-write`, `danger-full-access`) as a `permission` config option and switches it through `PermissionPresetService.set` — a live switch by design, applied at any point in the session and recorded in the session log, unlike the blank-only agent-preset switch. New sessions already start at `workspace-write` + approval prompts through the composed base defaults; the bridge neither changes nor re-derives that default, it only exposes it. The display copy is the acp deployment's own: the acp-app bundle restates the base preset table with the product `name`/`description` labels, because ACP clients render the wire name verbatim (the web, by contrast, localizes unlabeled presets through its client dictionaries).

## Consequences

Zed and every other ACP v1 client get a sign-in flow, a working mode switcher, and the complete plan-review loop over the automation bridge, while the automation contract keeps its one-shot permission semantics and its rule of never inferring a durable grant. Cancellation latency no longer grows with the handler count, so future agent-side methods can join the chain without rescheduling cancellation races — a property worth re-checking if the pinned SDK ever changes its dispatch model. Unrepresentable questions surface as the waterfall's no-answerer failure instead of a silently degraded dialog, so askers that need free text over ACP must wait for a request-input carrier in the protocol. The registry entry's version follows npm releases automatically; the only registry maintenance is the one-time stable-release PR and later distribution-shape changes.

## Alternatives considered

**A separate `dsh-zed-acp-adapter` bridging process** — rejected. An adapter speaking ACP to Zed and another protocol to dsh would re-implement the protocol server the bridge already is, add a process hop and a second session layer, and become one more consumer that every service-seam change must update. The plugin composition (`dsh --profile acp`) plus the registry's automatic npm version sync already deliver the decoupling such an adapter would promise.

**Advertising `allow_always` permission kinds** — rejected. The bridge is a machine-policy channel that never infers a durable grant from a client response; durable permissions belong to the deployment's permission policy, not to an automation transport.

**Gating `session/new` on the credential (`auth_required`)** — rejected for provider-agnosticism; see the decision above.
